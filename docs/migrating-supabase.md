# Moving the app to another Supabase project

Updated 29 October 2026.

## Source status

The source project `xiqfrvjasvcwywdyszta` is restricted by its egress quota, so
its REST API returns 402. The authenticated Supabase SQL Editor remained
available and read-only queries and bounded result downloads worked on
29 October 2026. Do not interpret a REST 402 as an empty database, and do not
run the REST-to-REST copier while the source is restricted.

Keep database passwords, service-role keys, and export files out of chat and
source control. The app's database is separate from the `.com` shared-hosting
deployment; do not point this app at the `.co.ke` VPS.

## Migration order

1. Confirm the destination project is the intended project and has no member
   data. Keep the source project intact until cutover is verified.
2. Run `supabase/bootstrap/schema.sql` once in the destination project's SQL
   Editor. It includes all 29 migrations in filename order and intentionally
   omits synthetic member-profile inserts. It still creates static catalogs,
   package tiers, and application defaults. It is for a fresh project only.
3. Export source rows from the authenticated SQL Editor in bounded JSON pages,
   download the result as CSV, and keep it local. The generated manifest records
   dependency order and row counts. `scripts/import-supabase-export.mjs
   --dry-run` validates the package without contacting the destination; the
   import uses restartable upserts and preserves IDs.
4. Move the `story-media` and `message-attachments` objects and verify their
   sizes/checksums. Profile photos are served by `genuinesugarmummies.com`, not
   these buckets.
5. Import into the destination, compare table counts, then test sign-in,
   messages, matches, package state, notifications, and media before changing
   any app configuration.
6. Only after verification, set the new Supabase URL and publishable/anon key
   in the `.com` app's shared-hosting configuration and update its host allowlist
   and CSP. Never put a service-role key in the client bundle.

Preserve primary keys. Foreign keys connect users, conversations, messages,
matches, settings, wallets, and other records; regenerating IDs breaks those
relationships. The importer uses the schema's actual conflict columns,
including composite keys for live viewers.

## Intentionally excluded

`password_reset_codes` is short-lived authentication material and should not be
carried to a new project. `email_outbox` and `email_queue` are not migrated, so
old queued mail cannot be replayed. Members can request a fresh reset code and
new mail is generated by the destination app.

The app does not use Supabase Auth for member accounts; it verifies passwords
against `public.users.password_hash`. Those hashes are part of the users table
export so existing accounts can continue to sign in.

before final cutover if the old app accepted writes after this snapshot.
